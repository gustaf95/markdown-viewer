# Markdown Viewer for Windows 요구사항 정의서

## 1. 프로젝트 개요

본 프로젝트는 Windows 환경에서 안정적으로 동작하는 데스크톱 Markdown Viewer를 개발하는 것을 목표로 한다. 사용자는 `.md`, `.markdown`, `.txt` 형식의 문서를 열어 한글, 영문, 코드 블록, 표, 이미지, 수식 등을 포함한 Markdown 문서를 정확하게 렌더링하여 확인할 수 있어야 한다.

실제 구현은 Claude Code를 사용하여 진행할 예정이므로, 본 README는 개발자가 바로 구현을 시작할 수 있도록 기능 요구사항, 기술 요구사항, UI 요구사항, 렌더링 요구사항, 테스트 기준을 정리한 문서이다.

---

## 2. 핵심 목표

- Windows에서 실행 가능한 Markdown Viewer 제공
- 한글 문서의 깨짐 없는 표시 지원
- Markdown 표준 문법 및 확장 문법 지원
- LaTeX 기반 수식 렌더링 지원
- 코드 블록 문법 강조 지원
- 로컬 이미지 표시 지원
- 사용자가 파일을 쉽게 열고 읽을 수 있는 간단한 UI 제공
- 향후 편집기 기능으로 확장 가능한 구조 확보

## 4. 권장 기술 스택

Claude Code가 구현할 때 다음 기술 스택 중 하나를 선택할 수 있다.

### 4.1 권장안: Electron 기반

| 구성 요소 | 권장 기술 |
|---|---|
| 데스크톱 프레임워크 | Electron |
| UI | HTML, CSS, JavaScript 또는 TypeScript |
| Markdown 파서 | markdown-it 또는 marked |
| 수식 렌더링 | KaTeX 또는 MathJax |
| 코드 하이라이팅 | highlight.js 또는 Shiki |
| 파일 처리 | Node.js fs API |
| 패키징 | electron-builder |

Electron은 Windows 데스크톱 앱 제작이 쉽고, Markdown 렌더링 생태계가 풍부하며, 수식·코드·이미지 표시를 웹 기술로 안정적으로 구현할 수 있다는 장점이 있다.

### 4.2 대안: Python 기반

| 구성 요소 | 권장 기술 |
|---|---|
| GUI | PySide6 또는 PyQt6 |
| Markdown 렌더링 | QWebEngineView + markdown-it/marked 번들 또는 Python markdown |
| 수식 렌더링 | KaTeX/MathJax HTML 삽입 |
| 패키징 | PyInstaller |

단, Python 기반은 WebEngine 포함 시 배포 파일 크기가 커질 수 있으므로 Electron을 우선 고려한다.

## 5. 주요 기능 요구사항

## 5.1 파일 열기

| ID | 요구사항 |
|---|---|
| F-001 | 사용자는 파일 열기 대화상자를 통해 Markdown 파일을 선택할 수 있어야 한다. |
| F-002 | 지원 확장자는 `.md`, `.markdown`, `.txt`를 기본으로 한다. |

| F-004 | 최근 열었던 파일 목록을 제공할 수 있어야 한다. |

## 5.2 Markdown 렌더링

| F-104 | 중첩 목록을 지원해야 한다. |
| F-105 | 인용문 `>`을 지원해야 한다. |

| F-107 | 링크 `[text](url)`를 지원해야 한다. |
| F-108 | 로컬 이미지 및 외부 이미지 링크를 표시해야 한다. |
| F-109 | GitHub Flavored Markdown, 특히 표 문법을 지원해야 한다. |

## 5.3 한글 지원

| ID | 요구사항 |
|---|---|
| F-201 | 한글 제목, 본문, 표, 코드 주석이 깨지지 않고 표시되어야 한다. |
| F-202 | 한글과 영문, 숫자, 수식이 혼합된 문서를 자연스럽게 표시해야 한다. |
| F-203 | 기본 글꼴은 Windows에서 가독성이 좋은 한글 글꼴을 사용해야 한다. 예: `맑은 고딕`, `Noto Sans KR`, `Pretendard` |
| F-204 | 줄바꿈, 문단 간격, 목록 들여쓰기가 한글 문서에서도 어색하지 않아야 한다. |
| F-205 | CP949 또는 EUC-KR 계열 파일을 열 경우 가능한 범위에서 자동 변환하거나 사용자에게 인코딩 선택 옵션을 제공해야 한다. |

## 5.4 수식 렌더링

| ID | 요구사항 |
|---|---|
| F-301 | 인라인 수식 `$...$`을 지원해야 한다. |
| F-302 | 블록 수식 `$$...$$`을 지원해야 한다. |
| F-303 | LaTeX 기본 문법을 지원해야 한다. 예: 분수, 첨자, 적분, 행렬, 그리스 문자 |
| F-304 | 한글 본문 중간에 포함된 수식도 깨지지 않아야 한다. |
| F-305 | 수식 렌더링 실패 시 앱이 멈추지 않고 오류 위치를 표시하거나 원문을 보여줘야 한다. |
| F-306 | KaTeX 또는 MathJax 중 하나를 사용하되, 오프라인 실행을 위해 필요한 스크립트와 스타일은 앱에 포함해야 한다. |

### 수식 예시

```markdown
인라인 수식 예시: $E = mc^2$

$$
\int_{0}^{\infty} e^{-x^2} dx = \frac{\sqrt{\pi}}{2}
$$
```

## 11. 구현 세부 지침

## 11.1 Markdown 처리

- Markdown 파서는 `markdown-it` 사용을 권장한다.
- 다음 플러그인을 검토한다.
  - `markdown-it-katex` 또는 `markdown-it-mathjax3`
  - `markdown-it-task-lists`
  - `markdown-it-anchor`
  - `markdown-it-footnote`
  - `markdown-it-container`
- HTML sanitize 처리를 반드시 적용한다.

## 11.2 수식 처리

- 빠른 렌더링과 오프라인 동작을 우선하면 KaTeX를 권장한다.
- MathJax는 호환성이 더 넓지만 상대적으로 무거울 수 있다.
- 기본 구현은 KaTeX로 시작하고, 필요 시 MathJax 옵션을 추가한다.

## 11.3 파일 인코딩 처리

- 우선 UTF-8로 읽는다.
- UTF-8 디코딩 실패 또는 깨짐 의심 시 CP949 디코딩을 시도한다.
- Node.js에서는 `iconv-lite` 사용을 권장한다.
- 사용자가 직접 인코딩을 선택할 수 있는 옵션을 제공하면 좋다.

## 11.4 로컬 이미지 경로 처리

- Markdown 파일의 위치를 기준으로 상대 경로를 해석한다.
- 예: `docs/sample.md` 내부의 `![img](images/a.png)`는 `docs/images/a.png`로 해석한다.
- 보안을 위해 허용 범위를 명확히 관리한다.

## 18. 가져오기(Import) 기능

내보내기의 반대 방향이다. HWPX·DOCX·HTML 문서를 읽어 Markdown으로 바꾼다.
내보내기가 `DocModel`을 거쳐 여러 형식으로 나갔듯이, 가져오기도 **여러 형식을 하나의
`DocModel`로 모은 뒤 Markdown 한 곳으로** 내보낸다. 변환기를 형식마다 따로 만들지 않기 위함이다.

```
내보내기 :  Markdown -> 보기용 DOM -> DocModel -> HTML / DOCX / HWPX
가져오기 :  HWPX / DOCX / HTML -> DocModel -> Markdown
```

### 18.1 요구사항

| ID | 요구사항 |
|---|---|
| F-1201 | `.hwpx`, `.docx`, `.html` 파일을 열어 Markdown으로 변환할 수 있어야 한다. |
| F-1202 | 변환 결과는 편집 모드에 바로 올라가고, 사용자가 확인한 뒤 `.md`로 저장한다. |
| F-1203 | 제목·문단·굵게·기울임·취소선·인라인 코드·목록·인용문·수평선을 복원해야 한다. |
| F-1204 | 표는 GFM 파이프 표로 복원해야 한다. |
| F-1205 | **수식은 LaTeX로 복원해야 한다.** 이미지로 떨어뜨리지 않는다. |
| F-1206 | 이미지는 문서 옆 `<문서명>_files/` 폴더로 꺼내고 상대 경로로 잇는다. |
| F-1207 | 코드 블록을 알아볼 수 있으면 펜스 코드 블록으로 복원한다. |
| F-1208 | 변환할 수 없는 요소를 만나도 중단하지 않고, 그 부분만 건너뛰고 계속해야 한다. |
| F-1209 | 원본 파일은 절대 수정하지 않는다 (읽기 전용). |

### 18.2 처리 흐름 — 내보내기와 대칭

내보내기에서 "DOM 해석은 renderer, 파일 생성은 main"으로 나눈 이유가 그대로 적용된다.
main에는 XML 파서가 없고 renderer는 sandbox라 파일을 읽지 못한다. 그래서 방향만 뒤집는다.

1. main: 파일을 열어 ZIP 압축을 풀고, XML 조각과 이미지 바이트를 꺼낸다
2. main -> renderer: `import:parse` IPC로 XML 문자열을 넘긴다
3. renderer: `DOMParser`로 XML을 파싱해 `DocModel`을 만든다
4. renderer: `DocModel` -> Markdown 문자열
5. renderer: 편집 모드에 올리고, 이미지 저장이 필요하면 main에 맡긴다

ZIP **읽기**가 새로 필요하다. `src/main/zip.ts`에는 쓰기만 있으므로 `readZip()`을 더한다
(`zlib.inflateRawSync`로 풀면 되고, 이미 있는 CRC 계산을 검증에 재사용한다).

### 18.3 수식 복원 — 이 기능의 핵심

내보낼 때 만든 변환기를 거꾸로 돌리는 일이다. 문법은 이미 실측으로 확인해 뒀다.

| 형식 | 원본 | 목표 | 참고할 코드 |
|---|---|---|---|
| HWPX | `<hp:script>`의 한글 수식 스크립트 | LaTeX | [src/main/hwp-eqn.ts](../src/main/hwp-eqn.ts) |
| DOCX | `<m:oMath>` OMML | LaTeX | [src/main/omml.ts](../src/main/omml.ts) |
| HTML | `<annotation encoding="application/x-tex">` | LaTeX | 그대로 꺼내 쓰면 된다 |

HTML은 우리가 내보낸 파일이면 KaTeX가 원본 LaTeX을 `annotation`에 남겨 두므로 **그대로 꺼내면 된다.**
나머지 둘은 실제 파싱이 필요하다.

**한글 수식 스크립트 -> LaTeX** 가 가장 손이 많이 간다. 토큰으로 끊어 트리를 만든 뒤 LaTeX으로 찍는다.

| 한글 수식 | LaTeX |
|---|---|
| `{a} over {b}` | `\frac{a}{b}` |
| `{a} atop {b}` | `\binom{a}{b}` 또는 `{a \atop b}` |
| `sqrt {x}` / `root {n} of {x}` | `\sqrt{x}` / `\sqrt[n]{x}` |
| `x^{a}` / `x_{a}` | `x^{a}` / `x_{a}` |
| `sum_{i=1}^{n} {...}` | `\sum_{i=1}^{n} ...` |
| `left ( ... right )` | `\left( ... \right)` |
| `matrix{a & b # c & d}` | `\begin{matrix}a & b \ c & d\end{matrix}` |
| `alpha` `pi` `GAMMA` `leq` `times` | `\alpha` `\pi` `\Gamma` `\leq` `\times` |
| `hat {x}` `vec {x}` `overline {x}` | `\hat{x}` `\vec{x}` `\overline{x}` |
| `"글자"` / `rm{글자}` | `\text{글자}` |
| `~` (온전한 한 칸) | `\ ` 또는 공백 |
| `+-` | `\pm` |

파서에서 조심할 것 (모두 내보내기 때 실측으로 확인한 사실이다):

- `#`는 행 구분, `&`는 열 구분이라 본문 문자일 때는 `\#` `\&`로 escape 되어 있다
- `^` `_`는 backslash escape가 없어 `"^"`처럼 따옴표 문자열로 들어 있을 수 있다
- 이름표는 공백으로 끊긴다. `pix`는 변수 `pix`이고 `pi x`가 π·x다
- 중괄호는 생략될 수 있다. `1 over 2`처럼 우리가 만들지 않은 문서도 읽어야 한다

**OMML -> LaTeX**는 `m:f`(분수) `m:rad`(근호) `m:sSup`/`m:sSub`/`m:sSubSup`(첨자)
`m:nary`(큰 연산자) `m:d`(괄호) `m:m`(행렬) `m:acc`/`m:bar`를 뒤집으면 된다.
`omml.ts`가 어느 MathML을 어느 OMML로 보냈는지 표로 남아 있으니 그 역을 따라가면 된다.

### 18.4 형식별 지원 범위

| 요소 | HWPX | DOCX | HTML |
|---|---|---|---|
| 제목 | 글자 크기·굵기로 추정 | 스타일 이름(`Heading N`) | `<h1>`~`<h6>` |
| 문단·글자 서식 | O | O | O |
| 목록 | 글머리 기호 추정 | 번호 매김 정의 | `<ul>`/`<ol>` |
| 표 | O (병합 칸 주의) | O (병합 칸 주의) | O |
| 코드 블록 | 고정폭 글꼴 + 음영으로 추정 | 같음 | `<pre><code>` |
| 이미지 | `BinData/` | `word/media/` | `<img>` (data URI 포함) |
| 수식 | `<hp:script>` 파싱 | OMML 파싱 | `annotation`에서 그대로 |

제목·목록·코드 블록을 **추정**해야 하는 것이 HWPX·DOCX의 약점이다.
우리가 내보낸 문서는 글자 모양이 일정해서 되읽기 쉽지만, 남이 만든 문서는 규칙이 제각각이다.
그래서 **우리 문서를 되읽는 것부터** 확실히 하고 범위를 넓힌다.

### 18.5 되돌릴 수 없는 것

미리 정하고 문서에 남긴다. 사용자가 기대를 갖지 않도록 변환 후 요약으로 알려 준다.

- 병합된 표 칸은 GFM 표로 표현할 수 없다 — 칸을 나누고 내용을 첫 칸에 몰아준다
- 글자 색·글꼴·크기 같은 서식은 Markdown에 대응이 없어 버린다
- 머리말·꼬리말·각주·주석·도형·차트는 버린다
- 여러 단 구성, 쪽 나눔은 버린다
- 코드 블록의 언어 이름은 알 수 없다 (구문 강조 색만 남아 있고 언어 정보는 없다)

### 18.6 단계별 계획

| 단계 | 범위 | 비고 |
|---|---|---|
| 1 | HTML -> Markdown | 가장 쉽다. renderer에 이미 DOM 파서가 있고 수식은 `annotation`에 그대로 있다 |
| 2 | HWPX -> Markdown (수식 제외) | ZIP 읽기 + OWPML 파싱. 되읽기 대상은 우선 우리가 내보낸 문서 |
| 3 | **한글 수식 스크립트 -> LaTeX** | 이 기능의 핵심. 토크나이저 + 파서 |
| 4 | DOCX -> Markdown | OMML -> LaTeX 포함 |
| 5 | 남이 만든 문서 대응 | 제목·목록 추정 규칙을 넓힌다 |

### 18.7 검증 방법 — 왕복 비교

내보내기가 이미 있으므로 **왕복 검증**을 자동으로 돌릴 수 있다. 이 기능의 가장 큰 장점이다.

```
test-docs/*.md  ->  HWPX  ->  Markdown  ->  원본과 비교
                ->  DOCX  ->  Markdown  ->  원본과 비교
                ->  HTML  ->  Markdown  ->  원본과 비교
```

- 완전히 같을 수는 없다 (공백, 글머리 기호 표기 등). **정규화한 뒤** 비교한다
- 수식은 LaTeX 문자열을 직접 비교하지 말고, **KaTeX로 다시 렌더링해 MathML이 같은지** 본다.
  `\frac{a}{b}`와 `\dfrac{a}{b}`처럼 표기가 달라도 뜻이 같으면 통과시켜야 한다
- 한글이 실제로 여는지까지 봐야 할 때는 내보내기에서 쓰던 절차를 그대로 쓴다
  (한글 COM으로 열기 -> PDF -> 이미지 -> 육안 확인)

### 18.8 UI

```
파일
 ├─ 열기...                Ctrl+O
 ├─ 가져오기               ▶ HWPX(한글)...
 │                          DOCX(Word)...
 │                          HTML...
 ├─ 내보내기               ▶ (기존)
```

- 가져오면 편집 모드로 열고 **아직 저장되지 않은 문서**로 다룬다. 사용자가 확인 후 저장한다
- 변환 중 버린 요소가 있으면 변환 후 요약으로 알려 준다 (예: "표 2개의 병합 칸을 풀었습니다")
- Drag & Drop으로도 받을 수 있게 한다 (확장자로 가져오기/열기를 구분)
